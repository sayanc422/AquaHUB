# The custom-tank enquiry form answers 503: the encryption key is missing

**Symptom:** a customer submits the tank enquiry form and the page says *"This form is not taking
enquiries at the moment."* `POST /v1/inquiries` returns `503` with a body like:

```json
{"reason":"inquiries.encryption-key is not set (INQUIRY_ENCRYPTION_KEY)",
 "runbook":"docs/runbooks/rotate-or-create-the-inquiry-key.md",
 "affects":"tank enquiries only; checkout, carts and orders are unaffected"}
```

`order-service` logs this once at boot:

```
WARN c.a.o.inquiry.TankInquiryRepository - tank enquiries are DISABLED:
inquiries.encryption-key is not set (INQUIRY_ENCRYPTION_KEY). Everything else in
order-service is unaffected.
```

**Nothing else is broken.** The pod is `Running`, every probe passes, and carts, checkout, the saga,
order lookups and the dispatch watcher all work normally. That is deliberate (ADR 0021): a missing
Secret for a bolt-on enquiry form must not be able to take the commerce path down with it.

**This is also the failure mode that hides.** The cluster looks entirely green while every customer
who uses the form is turned away. If you have just rebuilt the cluster, assume this has happened
until you have checked.

## Why this happens

`tank_inquiry` stores a customer's email, phone number and message encrypted, by Postgres, with
`pgp_sym_encrypt` ([ADR 0021](../adr/0021-encrypt-enquiry-contact-details-in-postgres.md)). The
passphrase comes from a Kubernetes Secret called `order-inquiry-key`.

**That Secret is not in this repository and must never be.** Every other secret here —
`platform-repo/dev/postgres/secret.yaml` — is plaintext in Git, which its own header admits is a
placeholder rather than a pattern. This key is the one that does not repeat that mistake, so
`bootstrap.sh` cannot create it and `kubectl apply -k` will not bring it back. It is created by
hand, once per cluster, and a cluster that is destroyed and recreated needs it again.

`scripts/bootstrap.sh` checks for the Secret before applying the `commerce` profile and **warns**
with the create command if it is absent. It does not stop, because the rollout genuinely is fine
without it. It does **not** create the key either: a key generated by a bootstrap script is a key
nobody wrote down, and the first `--destroy` would take every stored enquiry with it.

`order-service` refuses the *write* rather than falling back to a default key. A default would write
rows that look encrypted and are readable by anyone holding the source, and would make those same
rows permanently undecryptable the day a real key arrived. The refusal happens at the endpoint
rather than at startup so that the blast radius matches the feature — ADR 0021 states both the
reasoning and its cost, which is precisely that this failure is quiet.

The `secretKeyRef` in `platform-repo/dev/order/deployment.yaml` carries `optional: true` to make
that possible. Do not remove it: without it kubelet will not start a container whose environment it
cannot resolve, and the pod sits in `CreateContainerConfigError` with checkout down.

## Fix: create the key on a cluster that has none

```bash
kubectl create secret generic order-inquiry-key \
  --namespace aquashop-dev \
  --from-literal=INQUIRY_ENCRYPTION_KEY="$(openssl rand -base64 48)"
```

Then restart the pod, which is what actually picks the key up — an `env` from a `secretKeyRef` is
resolved once, at container start, so creating the Secret alone changes nothing in a running pod:

```bash
kubectl -n aquashop-dev rollout restart deployment/order-service
kubectl -n aquashop-dev rollout status deployment/order-service
```

Confirm the `WARN` is gone and the endpoint answers:

```bash
kubectl -n aquashop-dev logs deployment/order-service | grep -c 'tank enquiries are DISABLED'  # 0
```

**This restart takes checkout with it for the length of the rollout.** That is the one moment when
this feature does touch commerce, which is an argument for creating the Secret before the first
`commerce` rollout rather than after it.

**Keep a copy of the key somewhere outside the cluster before you do anything else.** There is no
secrets manager behind this. If the namespace goes and you have no copy, every enquiry already
stored is unreadable forever. To read it back out of the cluster:

```bash
kubectl -n aquashop-dev get secret order-inquiry-key \
  -o jsonpath='{.data.INQUIRY_ENCRYPTION_KEY}' | base64 -d; echo
```

(That is `base64 -d`, not decryption. A Kubernetes Secret is encoded, not encrypted, unless etcd
encryption-at-rest is configured — it is not, in k3d.)

The key must be at least 16 characters or the service refuses it as a placeholder. `openssl rand
-base64 48` gives 64.

## Rotation: there is no safe rotation, and you need to know that before you try

**Changing this key makes every existing `tank_inquiry` row permanently unreadable.** Nothing
re-encrypts them. `pgp_sym_decrypt` with the wrong key raises `Wrong key or corrupt data` rather
than returning rubbish, so the loss is at least obvious — but it is still loss.

If you must rotate, decrypt first, with the **old** key, and keep the output somewhere you are
willing to keep plaintext PII:

```bash
kubectl -n aquashop-dev exec -it statefulset/postgres -- psql -U orders -d orders <<SQL
SELECT id,
       pgp_sym_decrypt(email_enc,   '<OLD KEY>') AS email,
       pgp_sym_decrypt(phone_enc,   '<OLD KEY>') AS phone,
       pgp_sym_decrypt(message_enc, '<OLD KEY>') AS message,
       created_at
  FROM tank_inquiry ORDER BY created_at;
SQL
```

Then replace the Secret and restart:

```bash
kubectl -n aquashop-dev delete secret order-inquiry-key
kubectl create secret generic order-inquiry-key --namespace aquashop-dev \
  --from-literal=INQUIRY_ENCRYPTION_KEY="$(openssl rand -base64 48)"
kubectl -n aquashop-dev rollout restart deployment/order-service
```

Rows written under the old key stay in the table and stay unreadable. Delete them or accept them
as dead weight; nothing in the service will ever read them again.

## Reading an enquiry at all

There is no endpoint for this, on purpose — nothing in this platform has authentication, so an
unauthenticated read of this table would undo the reason it is encrypted. Until `staff-portal`
grows a login, reading an enquiry means a `psql` session by someone who holds the key:

```bash
kubectl -n aquashop-dev exec -it statefulset/postgres -- psql -U orders -d orders -c \
  "SELECT id, created_at, pgp_sym_decrypt(email_enc,'<KEY>'), pgp_sym_decrypt(phone_enc,'<KEY>'),
          pgp_sym_decrypt(message_enc,'<KEY>')
     FROM tank_inquiry ORDER BY created_at DESC LIMIT 20;"
```

**This is a gap, not a workflow.** It is recorded as one in ADR 0021.

## Are enquiries arriving at all?

This needs no key. `message_chars` is the one column kept in the clear precisely so this question
can be answered by someone who is not entitled to read the content:

```bash
kubectl -n aquashop-dev exec -it statefulset/postgres -- psql -U orders -d orders -c \
  "SELECT count(*), min(created_at), max(created_at), avg(message_chars)::int FROM tank_inquiry;"
```

`order-service` also logs one line per accepted enquiry, with the id and the message length and
nothing else:

```bash
kubectl -n aquashop-dev logs deployment/order-service | grep 'tank inquiry accepted'
```

## Verify the whole path

```bash
curl -ks https://aquashop.localtest.me/ | grep -c 'id="custom-tank"'          # 1
curl -ks -o /dev/null -w '%{http_code}\n' -X POST \
     https://aquashop.localtest.me/inquiries \
     --data-urlencode 'message=Runbook test, please ignore.' \
     --data-urlencode 'email=runbook@example.com' \
     --data-urlencode 'phone=9000000000'                                      # 303
```

Then check the count above went up by one, and delete the test row.

## In the AWS target

This runbook mostly does not exist. The key is a Secrets Manager entry read through IRSA, with
managed rotation and a versioned history, and the "decrypt everything first" dance above is
replaced by a KMS data key per row. None of that is built. Until it is, this page is the whole of
the key management story, and the manual step at the top is the price of not checking the key into
Git.
